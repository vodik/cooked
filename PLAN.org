* Operating protocol
:PROPERTIES:
:VISIBILITY: content
:END:

For an agent picking up work from this file.

1. *Pick.* Take the highest =NEXT= whose =:GATE:= is empty or satisfied. Never
   start a =TODO= that still has an unsatisfied gate — the gates exist because
   the change is unsafe without them. If nothing is =NEXT=, promote the first
   unblocked =TODO= in file order.
2. *Claim.* Set the task to =WIP= (this stamps a timestamp into =LOGBOOK=).
3. *Branch.* =git switch -c cooked/<short-slug>= off =main=, and record it in
   the =:BRANCH:= property immediately — before any code — so an interrupted
   session can be resumed.
4. *Work.* Read the cited =REPORT.org= section first. Launch a subagent only
   when the task says =:AGENT: yes=; otherwise do it inline.
5. *Verify.* Run what the task's =Done when= line names. A task with no
   verifiable outcome is not ready to start — say so rather than guessing.
6. *Hand back.* Set =REVIEW= and stop. Summarise: what changed, what the
   measurement said, and anything the report got wrong.
7. *Land.* Only on explicit say-so: =git switch main && git merge --ff-only
   cooked/<slug>=. If the fast-forward is refused, rebase the branch and ask
   again — never merge with a commit. Then set =DONE= and clear =:BRANCH:= to
   the merged SHA.

** Measuring in a real graphical frame

Batch mode measures spec construction and property application, never
rasterization — §7 item 8. Anything whose =Done when= line mentions a real
frame, a scroll, or redisplay needs a live pgtk frame, and this box can produce
one *headlessly*, so a measurement task does not need the user at the keyboard:

#+begin_src sh
gamescope --backend headless -W 1920 -H 1080 --expose-wayland -- \
  emacs -Q -l /path/to/script.el
#+end_src

=--expose-wayland= is load-bearing: without it gamescope offers only Xwayland
and an Emacs built =--with-pgtk= has no xdg-shell to bind. With it,
=display-graphic-p= is =t= and =framep= is =pgtk=. The script must end in
=kill-emacs=, and must write its numbers to a *file* — nothing on stdout
survives the compositor's own logging.

Two cautions. The frame comes up at Emacs' default size, not =-W/-H=, so call
=set-frame-size= explicitly and record the size next to the numbers. And
=(redisplay t)= — the =t= is required — is what actually costs time; a bare
=(redisplay)= is free to decide it has nothing to do. A 199×49 full-width
repaint calibrates at p50 ≈ 3.6 ms, so a no-op reading of ~0 ms means the
harness is wrong rather than the code being fast.

Two things to raise the rate for. gamescope's own frame callback becomes the
thing under measurement at the default refresh: every =max= pins to ~33 ms
(30 Hz) and p90 runs 3x p50 no matter what the code does. =-r 1000= moves the
tail to ~23 ms and leaves the median untouched — which is *why* medians are the
headline here, an instrument reason on top of the §9 A reason. Where it matters,
time the drain/apply separately from =(redisplay t)=; only the first half is
cooked's, and the split is what makes the compositor's contribution visible
rather than smeared through the number.

*pgtk is among the slowest Emacs redraw backends* — slow enough that smooth
scrolling is not reliably smooth on it. This cuts one way only, and it is worth
being explicit about the direction. A redisplay cost measured here is an *upper
bound*, so a *flat* redisplay result is conservative and a real regression would
show up here first and largest. What it does *not* license is reading a
redisplay figure from this harness as the cost a user on another backend pays,
or attributing a gap to cooked when the backend is a candidate. Any conclusion
of the form "redisplay is the bottleneck" needs a second backend before it is
load-bearing; "redisplay is *not* the bottleneck" is safe from here.

The load guard applies here more than anywhere: quiet the machine, and do not
fan out agents across a measurement task.

Conventions: =:GATE:= names a task that must be =DONE= first. =:GAIN:= is the
expected payoff, so a flat result is a finding rather than a failure. Waves are
=ORDERED= where the order is load-bearing; inside an unordered wave, pick freely.

*** What it says

*Rejoining costs nothing at ordinary wrapping and roughly doubles the p90 at
deep wrapping.* Both halves matter, and only the gesture harness can see either.

At no wrapping and at three screen rows per logical line the ratio sits on 1.0
and changes sign between runs — flat, on the same reading as the append cases
below. At ten rows per line the effect is unmistakable and it is *in the tail*:
the p90 ratio is 2.16 and 2.14 across two runs, stable to within a percent,
while the p50 ratio wanders from 1.30 to 1.88. *Report the p90 here* — the
median understates it and is the noisier statistic, which is the reverse of the
append case and of the §9 A default.

That tail *is* the symptom. Redisplay lays a continued line out from its start,
so most gestures move within a logical line and cost the same either way, and
every so often one crosses into a new one and pays for the whole thing. A
uniform 9 ms would not read as jerky; 9 ms with a 21 ms hitch every few gestures
does — which is what the 2026-09-05 note described as "the periodic ~19 ms hitch
as a scroll crosses into each new logical line".

*Reconciling with 2026-09-05*, which measured p50 7.42 / p90 19.81 on against
1.94 / 2.33 off: the p90 pair matches this closely and the effect is confirmed.
What did *not* reproduce is its size at *three* rows per line — that run's
"styled long prose" showed it where this content showed nothing. Settled below.

*Face density contributes, and it is not what 2026-09-05 saw.* Two separate
things fall out, and conflating them is how that run got read wrong:

1. *Styling roughly doubles a gesture outright*, at both wrap depths and with
   rejoining in either state — 3x goes 2.3 → 4.0 ms and 10x goes 2.8 → 6.2.
   That cost is the SGR runs themselves and has nothing to do with rejoining.
2. *Styling then amplifies the rejoin penalty, but only where the penalty
   already exists.* At ten rows per line the p90 ratio goes from a plain 1.2 to
   a styled 1.7, stable to within 0.1 across three runs. At three rows per line
   it stays flat and changes sign between runs, exactly as the plain content
   does — 0.77, 1.20, 1.24 is noise around 1.0, not an effect.

So the answer to the question left open above is *no*: face density does not
produce the effect at three screen rows per line, and the diff-hunk control was
right to rule it out. What remains for 2026-09-05 is the other branch — its
"styled long prose" was wrapping deeper than three rows, or its far wider
geometry (44x249, against 29x99 here) crosses logical lines more often per
gesture. Both are consistent with everything measured; neither changes the
conclusion, because both put the effect back at deep wrapping where the gesture
table already found it.

*One thing the small geometry says on its own*: plain 10x here is a p90 ratio
of 1.2, where the same content at 44x249 was 2.15. The blowup scales with
window width, which is the expected shape if the cost is laying out a continued
line from its start.

*** What this means for the subsystem

The =:GAIN:= — deleting =cooked--guard-row-width=, =cooked--wrap-cache= and
=cooked--mark-truncation= — is *live again*, but narrower than the report hoped.
The case for hard-splitting rows is a *tail-latency* case at deep wrapping, not
a throughput case: nothing measurable is lost at the wrapping a shell session
actually produces. Anyone making it should argue about the hitch. The
three-rows question is now settled and settles *against* deleting the
subsystem: the effect needs both deep wrapping and a wide window, and neither
is what a shell session ordinarily produces.

*** Superseded: the append run, and why it answered the wrong question

*For output arriving, the ceiling does not move.* Across twelve comparisons the
t/nil ratio sits on 1.0, wandering to either side of it — nine of the twelve are
within ±10%, and the direction is not consistent even for one content shape at
one geometry. This was first recorded as "suspect (ii) is not confirmed", which
was wrong: it is an answer about *appending*, and suspect (ii) is about
*scrolling*. Kept because it is a real answer to a real question, and because
the pgtk-vs-tty finding below came out of it.

The one apparent effect, +54% and +42% on 10x-wrapped apply, *did not survive a
change of geometry*: the same content at 64x115 gives 0.97, and on a tty 0.93.
Two runs agreeing is not two runs replicating when they share a configuration.
Treat it as unexplained and *not established* — if it is ever worth chasing, the
place to start is that it appeared only at ~29 rows on pgtk.

That conclusion — that the subsystem cannot be removed on a performance
argument — *stood only for appending*, and the gesture measurement above
supersedes it.

*** What the tty comparison found instead

Worth more than the thing it was run to check. At matched geometry (~65x115,
identical content):

| | pgtk | tty | pgtk/tty |
|-----------+-------+------+----------|
| apply | 11.4 | 4.8 | *2.4x* |
| redisplay | 5.9 | 1.7 | *3.5x* |

Both halves are the backend, and *apply is not supposed to be a backend cost at
all* — it is buffer manipulation. The 2.4x is the pixel-measuring inside it:
=cooked--guard-row-width= and =cooked--wrap-cache= ask the window for font
metrics on a graphical frame and get character counts for free on a tty. That is
where the subsystem's cost actually lives, and it is paid whether or not
anything is wrapped — the "no wrapping" row shows the same 2.4x.

*This relocates the optimisation target.* The question is not rejoin-vs-split,
it is whether the guard can answer from a cheaper source on a graphical frame.
Note also that pgtk apply scales hard with row count (2.3 ms at 29 rows, 11.4 ms
at 64) where tty does not — consistent with a per-row measurement, and a good
sanity check on the reading.

Keep =emacs -nw= under foot as a standing comparison point for anything that
touches the guard or the wrap cache: it is the control that says whether a cost
is cooked's or the backend's.

*** An unrelated finding, worth its own task

Every run held roughly *twice* the buffer chars under =rejoin=t= as under =nil=
for the identical byte stream at 10x wrapping — 2,670,358 vs 1,176,739 in the
tty run — while a 20-burst probe with no eviction showed 198,221 vs 200,000. So
*scrollback eviction is counted in lines*, and hard-splitting multiplies the
line count by the wrap factor: =rejoin=nil= retains about half the *text* for
the same configured scrollback. Anyone arguing for the split-row bet has to
answer this, because the same setting would then mean two different amounts of
history.

is parsed to a symbol from a closed set plus an integer, so the rendering is
built entirely from cooked's own vocabulary. Anything unparseable leaves the

a wrong number and go quiet.

*§8 is wrong about RIS being a Lisp-only change.* There was no Lisp-visible RIS

*** A pre-existing bug this turned up, and the pattern behind it

** REVIEW [#C] Glyph scaling before trimming
:PROPERTIES:
:EFFORT:   2d
:REPORT:   §2 "The framing that matters: repair vs destroy"
:BRANCH:   d7007db
:END:
Turns a destructive repair into a non-destructive one. Needs a metrics cache
first, or it will =font-at= per cell per drain. Use ghostel's key shape with
cooked's stamp invalidation — =cooked--wrap-cache= is already stamped on font,
=face-remapping-alist= and geometry. Load-bearing details: the three-way min of
width/ascent/descent ratios, and the =floor(pixel_size x scale) / pixel_size=
quantization.

*** Measured first, and §2's plan is wrong about where the hook goes

Probed in a real pgtk frame on this machine's default font — 9x20 cell, default
ascent 15, descent 5:

| glyph                   | width | slot | ascent | descent | overflows |
|-------------------------+-------+------+--------+---------+-----------|
| =a=, =─=, =│=, =░=, =▓= |     9 |    9 |     15 |       5 | —         |
| 文                      |    15 |   18 |   *18* |       5 | *height*  |
| 🙂                      |  *19* |   18 |     14 |       4 | *width*   |

*Both hazards are live, and they are different defects.* The emoji is one pixel
over its two-cell slot, which accumulates across a row and eventually
soft-wraps — the case the guard already catches and repairs destructively, and
the one §2's "step 2.5 inside =cooked--guard-row-width=" is written for.

*The CJK case has no repair at all today, and the guard cannot see it.* 文 has
an ascent of 18 against the default 15, so a row holding one is *23 pixels tall
against 20* — measured, 15% over — while the width fits comfortably. The guard's
only question is =cooked--row-wraps-p=, and for that row it answers *nil*. So
scaling hung off the wrap check would never fire for the offender that is
actually mispainting.

This also confirms *why the three-way min is load-bearing*, with numbers rather
than by assertion: for 文 the sum ratio is 20/23 = 0.87 and the ascent ratio is
15/18 = 0.83, so scaling by the sum leaves the ascent over the line.

The consequence beyond ugliness: =cooked--window-rows= divides the window's
pixel height by =window-default-line-height= to tell the child how many rows it
has, so rows 15% taller than that divisor mean the grid and the display disagree
about how many rows fit. Same class of hazard =default-text-properties nil= was
set to prevent (§7), reached by a different route.

*** How the trigger has to change

Not "did the row wrap" but "does this row hold a glyph exceeding its slot in
*either* dimension". The cost is controlled by the gate already there: step 1's
=cooked--row-mismeasured-p= skips a uniform row in a fixed-pitch font, which is
the overwhelming majority and cannot hold an offender. Only what survives that
gate needs a per-cluster measurement, and only the first sighting of each
cluster needs a real one.

*** Landed, and what it does

Measured live in a pgtk frame, same 9x20 cell:

| input      | height  | width               |
|------------+---------+---------------------|
| =abc文def= | 23 → 20 | 69 → 72             |
| =abc🙂def= | 20      | 73 → 72             |
| =abcdef=   | 20      | 54, untouched       |

The CJK width *rising* is correct rather than a regression: =min-width= holds
the glyph at the two cells the grid budgeted, where before it under-filled them
at 15px. Eight cells of grid is now 72 pixels of display, which is the alignment
the guard exists to keep.

Step 2.5 runs *before* the wrap question rather than after it, per the finding
above. =cooked-glyph-scale-floor= (0.5) is the point at which the repair stops
repairing and starts hiding — below it, an unreadable glyph in the right place
is worse than a truncation arrow saying plainly that something did not fit. nil
restores the old trim-only behaviour.

The metrics cache shares =cooked--wrap-cache='s stamp rather than keeping its
own: the stamp is the expensive part, 44 µs against the ~20 µs the guard is
trying to get down to, so a second cache with a second stamp would cost more
than either table saves. A border row of 500 identical characters is one shaping
call and 499 hash lookups.

=cooked--glyph-scale= takes a slot in *pixels* rather than cells, so it is
arithmetic and nothing else — cells would mean asking =frame-char-width=, which
answers 1 on a terminal frame and would make the function untestable in batch
for a reason unrelated to what it computes. The three-way min and the pixel
quantization are unit-tested there; the rendering is verified by script, since
batch has no glyphs.

*** The drawing half is not done, and the geometry hid that

Rendered to PNG and *looked at*, which the pixel measurements could not
substitute for. The box aligns now — the =│= separators line up with the =┬=
and =┴= where before they did not, and every row is the same height. But a
shrunk glyph is *left-aligned in its slot*, so =abc文def= draws with a visible
gap between 文 and =def=.

The arithmetic says why, and it is not a tuning problem. The three-way min picks
the *ascent* ratio for CJK, 0.83, because that is the binding constraint — but
=height= scales the font *uniformly*, there being no vertical-only scale in
Emacs, so a height-bound glyph necessarily comes out narrower than its slot.
15px becomes ~12.5px inside 18px, and =min-width= pads the difference entirely
on the right.

So the trade actually made is: *the gap after a CJK character grows from 3px to
5.5px, in exchange for the row no longer being 15% too tall.* Better, and not
right.

*ghostel has the same artifact*: its display spec is the same two properties
with no centring. Its =adjustWidth= sidesteps the *width* case differently — a
lone glyph claims the next cell rather than shrinking, hiding the following
space — but that does nothing for the height-bound case, which is the one live
on this font.

What is needed is a *position*, and Emacs offers no way to centre a glyph inside
its own =display= spec. The candidates, none tried:

1. Pad symmetrically by putting a =(space :width …)= display on the *neighbouring*
   cells rather than on the glyph. cooked owns the whole row, so it can — but a
   cell is only free if it holds a space, and cooked would then be rewriting
   cells the grid did not damage.
2. =:align-to= on a zero-width space inserted before the glyph. Adds a character
   to the buffer, which breaks the one-buffer-character-per-cell invariant the
   guard and the seam both depend on.
3. Accept left alignment and *reduce how much shrinking happens*, by taking
   ghostel's claim-the-next-cell path so the slot grows instead of the glyph
   shrinking. Helps the width case; the CJK ascent case still shrinks.
4. Leave it, and treat the gap as the price of alignment.

*Do not close this task on the geometry alone.* That is what nearly happened
here: every pixel measurement said it worked.

*** Borrowed from ghostel after a closer read (2dda682)

Two things its =Renderer.zig= has that the first pass did not.

*The metrics key includes the face.* ghostel keys on =style_id=; cooked keyed on
text alone, which hands a bold glyph the regular one's measurements. A bold face
is a different font and so a different glyph. Straight correctness fix.

*=adjustWidth=, the claim path* — and it is a better idea than the one it sits
beside. A glyph too wide for its cell does not have to be made *smaller* if
there is somewhere for it to *go*. Given two cells it is scaled less, or not at
all, and the leftover gap is exactly what scaling costs, so the cheapest gap is
the one never opened. It runs *before* the scaling: widen the slot where that is
free, then scale whatever is still over. The claimed space is hidden with
=(space :width 0)= rather than deleted — a space at zero width is still a space
in the buffer, so the yank, the search and =cooked--check-seam= all still see
what the child sent.

*It does not help the CJK case*, and neither does ghostel's: both skip claiming
for a glyph that is already two cells wide (=if (cell.wide) return 2=). So the
left-alignment gap above stands in both projects.

*** It shipped broken, and how

Reported from real use: htop out of line where it had rendered perfectly, btop a
mess, =tree= with an extra line of coloured corruption between every =│=, and
scrollback in a large directory very slow. Off by default now (feff41b) and the
cause fixed (788bff3), but *both* diagnoses on the way are worth keeping.

*The first guess was wrong.* Box-drawing glyphs coming from fallback fonts with
roomier metrics, firing the scaler — plausible, and false. Measured, every one
of =─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼ █ ▊ ▎ ░ ▒ ▓ ⣿ ❯= comes from the *default* font at
exactly 9x15/5. They were never scaled at all.

*The damage came from the path added to avoid scaling.* A box character has
exactly cell-shaped proportions — 9 over 20 against a cell of 9 over 20 — so
=cooked--glyph-claims-next-cell-p= compared two equal aspects, answered yes on
the =>==, claimed the cell after it and hid the space living there. Every line
of =tree= output begins =│ = and every one did it: 8 display properties and 4
hidden spaces over three lines.

The missing piece is ghostel's *first act* in =adjustGlyph=, which returns
before doing anything when the glyph's width is exactly its slot and its ascent
and descent are exactly the default's. It reads like an optimisation and is not:
it is what keeps the claim path away from glyphs that need neither.

*And the buffer text was correct throughout*, which is why nothing in the suite
caught it — a text oracle cannot see a bug that lives entirely in what is hung
on the text. The regression test asserts the *absence* of a decision.

**** Done: pixel-delta wheel accumulation (cfe4e85)

Both guards are ghostel's and both are the whole difficulty. A real mouse is
excluded by *device class*, not by the delta — X11 and pgtk report a notch as
several rows of pixels with no line count, which arithmetic cannot tell from a
fast swipe, so a notch would be accumulated, rounded, and a click would go
missing. And the floor of one press is the event's own *line count*, not a
constant: macOS reports a notch as one line and fewer pixels than a row when
=line-spacing= is set, so the row arithmetic yields zero and the notch vanishes.

**** Done: fish injected (754493e); nushell declined

docstring said injecting would mean being right about =-C= ordering and

**** Declined: kitty transmission by file (75d32c6)

**** Done: the kitty flags (d633794), and bash < 4.4 declined (c13973e)

about how a key is spelled. A child that asks for associated text, is told yes,
and encodes for it has been *actively misled*; one told no falls back to a
spelling that works. Only the reply is masked; the stack keeps what the child
pushed, because a pop must restore what its push put there.

bit 1 plus the alternate-keys bit cooked ignores.

** DONE [#C] Prebuilt module download
:PROPERTIES:
:EFFORT:   2d
:REPORT:   §3 "Prebuilt module download"; "The artifact has to carry terminfo"

*The digest closes the hole only because two escape hatches were removed*, and
that is the substance of it. ghostel's =latest= download is *deliberately not
ported* — there is no pinned digest for a moving target, so =latest= would be a
path on which verification silently does not happen, which is exactly the
\"download proceeds anyway\" failure. And an asset with no pinned digest is
refused *before the fetch*, so there is no \"could not verify, continuing\".

What it does *not* do is defend the release: whoever can write the constant can
write the artifact. It moves the trust root from the CDN to the git tag, not to
a key, and the docstring says so rather than letting a reader assume a signature.

*Staleness is a branch, not a replacement* — §3 reads as the latter and must not
be. Sidecar present → compare the terminfo digest; no sidecar but source present
→ the old mtime rule, which catches an edit made a second ago that no sidecar
can; neither → face value. And a *digest* rather than a version number, because a
hand-bumped version is a constant nobody remembers to move — a test recomputes
it from the checkout, so forgetting fails the suite.

*Bug found on the way*: Emacs' auto-compression is keyed on the destination
being named =.tar.gz=, and jka-compr skips content already carrying the gzip
magic — so a healthy artifact is written verbatim *by luck*, while an HTML error
page served with a 200 gets gzipped on the way to disk and then fails its digest
with a story about tampering.

*Unwired, as expected*: no release publishes artifacts, so the command declines
and says why. §3's \"~30 lines\" is the digest comparison only; a download
actually safe to load is ~200 lines plus the Makefile side.
Port the sidecar read *before* =module-load= (so a stale =.so= is refused),
atomic install-by-rename, never prompting at load time. Then do what ghostel
did not: publish =SHA256SUMS= and verify against digests compiled into the
=.el=, so the trust root is the package rather than the CDN.

*The artifact must carry terminfo*, and that changes staleness from
mtime-vs-source to version-vs-sidecar — a downloaded install has no
=terminfo/cooked.ti= to compare against.

Reproduced and attributed. =tree -C /usr/include= in a 100×32 pgtk frame under

=cooked--drain-and-apply= — cooked's Lisp, not redisplay and not the

*The cause was a stale docstring describing an invariant the code did not

per render pass and passed down, rather than asked per character".
=cooked--apply-deco= asked =cooked--layout-window= and =cooked--deco-cell-size=

| =cooked--layout-window= calls / session | 172,224 |     17 |
| same under =--batch=, tty frame         |  330 ms | 210 ms |

*Rust.* A reserved =BoxGlyph::BLANK= — descriptor 0, which no codepoint

trailing blanks, with no trimming step: a blank run at the end of a row has no
glyph run after it and is refused structurally. That matters on a wrapped row,
where =Row::line_runs= hands over the full width and the padding out to the

A post-pass rather than a rule in each builder, because there are three of them
— =build_runs=, =build_plain_runs= and the =#[cfg(test)]= =runs_to_reference=

*Correction to the design: U+00A0 is a blank too.* The task said "a plain
space". tree(1) 2.3.2 does not indent with one — it emits

the win. =draws_nothing= is therefore a two-element list, and deliberately a
short closed list rather than a Unicode property: what qualifies is a character
the child used as spacing *between box glyphs*, and baking anything else into a
run's bitmap would hide something the child meant to be seen.

*Lisp.* A decoration record is now =(glyph PATTERN COLUMN ROW)=, PATTERN being

*** The four rules, and where each one lives

=cooked--glyph-run-segments= is the one place a run is cut, and it argues both
of the rules that survive to Lisp. The other two never reach it.

- *Style, underline or link* split the run on the wire, in =Row::build_runs=,
  exactly as before — so they arrive as separate =PACKED= strings and there is
  nothing here to do.
- *A shade* breaks it one cell at a time, unchanged. Verified still holding by

  shade rule and the absorbing rule meet, and the blank between two shades has
  to come out as a segment of its own.
- *The cursor's cell* breaks it, new.
